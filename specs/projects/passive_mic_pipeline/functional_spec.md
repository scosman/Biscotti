# Functional Spec: Passive Mic Pipeline

Background and evidence: [research summary](../../research/builtin-mic-voice-processing/summary.md). Product context: [project_overview.md](./project_overview.md).

## 1. Goal

Replace Biscotti's VoiceProcessingIO (VPIO) mic capture with **one** pipeline that works on every input device and leaves the user's meeting untouched:

- **Capture:** a passive raw tap that never changes shared audio state, and records every channel that carries signal.
- **Processing:** offline, as part of transcription. It picks or combines the right mic channels, cancels echo using Biscotti's own system-audio track as the reference, and levels both tracks.

## 2. Principles (apply to every decision below)

1. **The meeting always wins.** Starting, running or stopping a Biscotti recording must never change another app's mic signal, the output device's sample rate, or other apps' playback volume.
2. **One pipeline.** One capture path and one processing path for every device. No per-app or per-device user settings. Options may exist for testing, but the app ships one default.
3. **Raw is ground truth; processed is derived.** Capture writes what the hardware delivered, as complete as storage policy allows. Processing never modifies raw files. Its outputs can be regenerated by re-running it, including on older recordings and on future versions of the algorithms.
4. **Never lose data.** A channel that carries signal is never discarded by a live guess. Any channel selection happens offline, with the whole recording in view.
5. **Degrade gracefully inside the one pipeline.** Each processing stage either succeeds or is skipped with a recorded reason. Processing never fails transcription for a reason a simpler path could survive.
6. **Measure, don't guess.** Open questions (storage policy, echo engine, AAC reference quality) are answered by automated tests and the Mic Pipeline Lab before defaults are locked.

## 3. Scope

**In scope**

- `AudioCapture`: a new passive mic engine becomes the default. It writes multichannel segment files, writes timeline sidecars for mic and system, and wires live levels. VPIO is kept only as a non-default mode for side-by-side comparison.
- New `AudioProcessing` package:
  - decoding;
  - channel analysis and combining;
  - track alignment;
  - echo cancellation (with a bake-off between engines);
  - levelling and limiting;
  - mixing;
  - writing the processed mic file;
  - the processing report;
  - a CLI;
  - a test-signal kit.
- `Transcription` uses `AudioProcessing` instead of `AudioMerger` (the transcription, speaker-analysis and voiceprint-backfill paths all go through it).
- Meeting playback prefers the processed mic file when it exists.
- ManualTestApp **Mic Pipeline Lab** tab, plus a `mic_pipeline` manual-test script (`mp_*` steps).
- Docs: research README updates, CLAUDE.md (staleness rule for `mp_*`, package list), and third-party notices.

**Out of scope** (possible follow-ups; not in this project)

- Live or streaming processing during recording, including the live transcript (PR #127).
- An input device or channel picker UI (#116).
- An app-side mic level meter or "silent mic" warning UI. The capture layer exposes the signals; the lab uses them.
- "Me" attribution from track provenance.
- Reference-free noise suppression or voice isolation, which the research shows tends to hurt Whisper.
- A user-facing setting for the pipeline choice. That is decided at Checkpoint 2 and built afterwards if wanted.
- Deleting the VPIO engine code. Also decided at Checkpoint 2.

## 4. Features and behaviour

### F1. Passive capture (AudioCapture)

**F1.1 No shared-state changes.** The default mic engine:
- does **not** enable voice processing;
- does **not** change any device's sample rate (no `ensureOutputRateMatchesInput`);
- does **not** configure ducking;
- does **not** attach any output node.

It follows the system default input device, as today.

**F1.2 What is written for each recording**, in the meeting directory (exact names in [architecture](./architecture.md#file-layout)):

| File | When | Contents |
|---|---|---|
| `mic.aac` | Always | Mono ADTS AAC-LC at 24 kHz and 64 kbps, as today. Crash-safe, playable and transcribable on its own. 1-channel input is passed through. Multichannel input becomes the **mean of the live channels** (see F1.3). |
| `mic.seg<K>.ch<N>.aac` | Only for **multichannel segments**: the device delivered more than one channel, and the channel-file policy is on | One mono ADTS AAC file per device channel, at the same encoder settings. Segment K covers one continuous run of a single device format. |
| `mic.timeline.jsonl` | Always | Append-only event log: start, format and device per segment, gap fills, reconnects, segment ends (including dead channels), stop. |
| `system.aac` | Always | As today. |
| `system.timeline.jsonl` | Always | Start (including leading-silence frames), gap fills, reconnects and format changes, stop. |
| `system.ref.caf` | Only when `writeSystemPCMReference` is on (lab only) | Uncompressed Float32 mono copy of the system tap, used to test whether the AAC reference limits echo cancellation. |

**F1.3 Live and dead channels.** Within a segment, a channel becomes **live** the first time its peak exceeds −100 dBFS, and stays live for the rest of that segment.
- `mic.aac` uses the mean of the live channels. If no channel is live yet, it writes digital silence.
- At segment end, the files of channels that never became live are **deleted**, and listed as `deadChannels` in the timeline.
- No channel that carries signal is ever dropped.

**F1.4 Device channel cap.** Only the first 16 channels of a device are captured; anything above that is logged once. (Interfaces with more than 16 inputs are out of scope.)

**F1.5 Format flips and route changes.** When the device's format changes (for example the built-in mic going from 1 to 3 channels because a VPIO meeting app started a call), or the default input changes:
- the engine rebuilds itself;
- `mic.aac` continues, with silence filling any gap longer than 100 ms, as today;
- the current segment ends and a new one starts if the new format is multichannel;
- the timeline records each event.

Recording never stops because of a format flip.

**F1.6 Levels and liveness.** `CaptureState` exposes, at least 5 times a second:
- `micLevel` and `systemLevel` (RMS, 0…1);
- `micChannelLevels` (peak per channel, up to 16);
- `micChannelCount`;
- `micDeviceIsBuiltIn`;
- `micSuspectedSilent`: true once every captured mic channel has stayed below −90 dBFS for the last 30 s of recording, false otherwise. Not raised in the first 30 s, and it resets as soon as any channel rises above −90 dBFS.

The app UI does not consume these in this project; the lab does.

**F1.7 Built-in mic detection.** A device is "built-in mic" only when its transport type is built-in (`bltn`) **and** its UID is `BuiltInMicrophoneDevice`. Matching on the device name is forbidden. The headphone-jack mic is also built-in transport, but has a different UID.

**F1.8 Mic modes (comparison only).** `MicCaptureMode` has two values:
- `.passive` (the default, and the only mode the app uses);
- `.appleVoiceProcessing`, the existing VPIO engine, unchanged.

The lab uses the second for side-by-side comparison. VPIO mode writes only `mic.aac` and `mic.timeline.jsonl`; it never writes channel files.

**F1.9 Unchanged behaviour.** All of these stay as they are:
- startup ordering, where the mic's first buffer anchors t=0 and the system track is padded to match;
- startup retries;
- system-tap retries;
- the permission flows;
- `requestPermissions`;
- crash safety of `mic.aac` and `system.aac`.

### F2. Offline processing (AudioProcessing)

**F2.1 Trigger.** Processing runs inside the transcription step, in the Transcriber XPC service, whenever the existing code would have merged mic and system audio:
- transcription;
- `SpeakerAnalyzer`;
- voiceprint backfill.

It also runs on demand from `audioproc-cli` and from the lab.

**F2.2 Inputs.** The meeting directory's files, discovered from the `mic.aac` path:
- `mic.aac`;
- the channel files listed in the timeline;
- both timelines;
- `system.aac`;
- optionally a reference override (`system.ref.caf`).

Missing optional inputs are fine. Without a timeline (older recordings, or VPIO-era ones), the pipeline treats `mic.aac` as one mono segment and `system.aac` as one segment.

**F2.3 Stages, in order:**

1. **Decode** every input to 16 kHz mono Float32.
2. **Combine the mic channels.**
   - For each multichannel segment, analyse every channel over the whole segment and choose a combination plan: a single channel, or a lag- and polarity-aligned weighted sum.
   - Regions that no channel segment covers use `mic.aac`.
   - Design: [audio_processing.md §Channel analysis](./components/audio_processing.md#channel-analysis).
3. **Align.** Estimate the echo delay and drift between the system track and the mic, per continuous segment, and decide whether echo is present at all. If confidence is low (for example on headphones), echo is "not detected" and AEC is skipped for that segment.
4. **Cancel echo** with the selected engine on segments where echo was detected, using the aligned system track as the reference.
5. **Level each track.** Speech-gated dynamic gain toward a target speech loudness, then a peak limiter. Mic loudness is measured only on frames where the far end is quiet, so echo never drives the mic gain.
6. **Mix** the levelled mic and system, then limit the result. This 16 kHz mono mix goes to WhisperKit and SpeakerKit, replacing `AudioMerger`'s output.
7. **Write `mic.processed.aac`**, the levelled, echo-cancelled mic for playback: 16 kHz mono AAC, written atomically. Failure to write is logged and is not fatal.
8. **Write `processing.report.json`** (best effort), recording what every stage decided and measured.

**F2.4 Degradation rules.**

| Failure | What happens |
|---|---|
| A channel file is unreadable | Skip that channel. If none are usable, use `mic.aac` for the segment. |
| Alignment confidence is low | Skip AEC for the segment; the reason is recorded. |
| The AEC engine fails | Skip AEC for the segment; record the error. |
| `system.aac` is missing or empty | Mic-only processing: level the mic, no AEC. |
| `mic.aac` is missing or empty | System only. |
| Both are missing | Throw `invalidInput`, as today. |

Levelling, limiting and mixing are pure and cannot fail on valid input.

**F2.5 Determinism.** The same inputs and options produce bit-identical outputs on the same machine and engine version. No randomness at runtime; all estimators are deterministic.

**F2.6 Performance budget.** On Apple silicon (M1 baseline):
- end-to-end processing takes at most **10% of the recording's duration** with the selected engine, single meeting;
- peak extra memory is at most about 2 full-length 16 kHz mono buffers plus O(window) scratch (about 460 MB for 60 minutes; today's merge already holds about 690 MB).

**F2.7 Options** (`ProcessingOptions`; the defaults are what the app uses):

| Option | Default | Purpose |
|---|---|---|
| `echoCancellation` | selected engine (after the bake-off) | `.off`, `.webRTCAEC3` or `.localVQE` |
| `leveling` | `.on` | `.off` gives a plain sum plus limiter: the "None" UX option |
| `channelPlanOverride` | `nil` | Lab only: force mono-mix-only or a single channel |
| `referenceOverride` | `nil` | Lab only: use `system.ref.caf` |
| `writeProcessedMic` | `true` | |
| `writeReport` | `true` | |

### F3. Echo engine bake-off

**Candidates:** WebRTC AEC3 (BSD-3) and LocalVQE v1.4-AEC (Apache-2.0), both vendored as source and built as SPM targets. **Fallback:** SpeexDSP, used only if neither candidate can be packaged.

**F3.1 Packaging gate.** An engine enters the bake-off only if all of these hold:
- it builds and passes tests in CI (`make ci` on macos-15 with Xcode 26.3);
- it needs no network access at runtime;
- it bundles everything it needs;
- its licence is permissive.

An engine that fails the gate within Phase 3 is dropped from the bake-off, with the reason recorded in the bake-off report.

**F3.2 Scenario matrix**, run by `audioproc-cli bakeoff` on the test-signal kit's real-speech scenarios:

| ID | Scenario |
|---|---|
| S1 | Linear echo, far-end only |
| S2 | Soft-clip (laptop speaker) nonlinearity |
| S3 | Double-talk |
| S4 | Clock drift of 100 ppm |
| S5 | AAC-coded reference |
| S6 | Echo delay of 800 ms |
| S7 | No echo (headphones) |

**F3.3 Gates and initial targets.** The report records actuals whatever happens.

| Measure | Target |
|---|---|
| Median far-end-only ERLE, S1 | ≥ 25 dB |
| Median far-end-only ERLE, S2 and S5 | ≥ 15 dB |
| Near-end SI-SDR, S3 | ≥ input + 3 dB, and near-end-only regions ≥ 20 dB |
| S7 | Echo not detected; output SI-SDR vs input ≥ 25 dB |
| Real-time factor | ≤ 0.1, single process, CI runner |

**F3.4 Selection rule.**
- Score = sum of ERLE over S1, S2 and S4–S6, plus 2 × the double-talk SI-SDR gain, computed among engines that pass every gate.
- If both engines are within 10% of each other, choose AEC3: simpler, cheaper, and best-known.
- If no engine passes every gate, choose the highest score and flag it in the report for Checkpoint 1.

The selected engine becomes the default `echoCancellation`. Checkpoint 1 confirms or overrides it on real recordings. The losing engine is removed in Phase 6.

### F4. Storage experiment (answered at Checkpoint 1)

Questions, focused on the built-in mic:

1. Which channel counts and rates does the built-in mic deliver to a passive tap when idle, and during Chrome/Meet, a Slack huddle, native Teams, Zoom and FaceTime?
2. What does storage cost, in MB per recorded hour:
   - for `mic.aac` vs. the channel files;
   - for digitally silent and near-silent channels, measured?
3. On the built-in mic, does the channel-plan result (from the channel files) beat the mono-mix-only result (`mic.aac`)? Judged by metrics (speech level, noise floor, SNR estimate) plus listening.

Policy options. **Until Checkpoint 1, D1 is the default.**

| Option | Policy |
|---|---|
| D1 | Write the channel files and keep them |
| D2 | Write them, then delete them after processing succeeds (keep `mic.aac` and `mic.processed.aac`) |
| D3 | Don't write channel files for the built-in mic; write them for other multichannel devices |
| D4 | Never write channel files |

**Decision rule** (proposed, final call at Checkpoint 1):
- If the channel plan is not measurably better than mono-only on the built-in mic → D3.
- Otherwise, if channel files are more than 2× the size of `mic.aac` per hour → D2.
- Otherwise → D1.

Multichannel interfaces keep their channel files under every option except D4, because live channel guessing is ruled out.

### F5. AAC reference check (answered at Checkpoint 1)

The lab records with `writeSystemPCMReference` on, then processes the same recording twice: once with `system.aac` as the reference, once with `system.ref.caf`. It shows ERLE estimates for each.
- If the PCM reference gains less than 6 dB of ERLE, AAC is good enough. Nothing changes.
- Otherwise, Phase 6 turns on `writeSystemPCMReference` in production, and deletes `system.ref.caf` after processing succeeds.

### F6. Mic Pipeline Lab (ManualTestApp)

A new tab, plus a `mic_pipeline` script. Full design in [components/mic_pipeline_lab.md](./components/mic_pipeline_lab.md). The lab must let a human:

1. **Watch live input:** device (name, UID, transport, built-in flag), mode (channel count, rate), per-channel meters, the system meter, the silent-mic flag, and a timeline event log.
2. **Record a session** with capture options:
   - mic mode (passive or Apple voice processing);
   - channel files on or off;
   - PCM reference on or off.
3. **Process the session** in variants:
   - mono-only, best single channel, or channel plan;
   - AEC off, AEC3, or LocalVQE;
   - AAC reference or PCM reference.

   For each variant it shows a metrics table.
4. **Listen and compare:** raw channels, `mic.aac`, each processed variant, and a VPIO-mode recording.
5. **See storage:** bytes and MB/hr per artifact, plus the projected MB/hr under each of D1–D4.
6. **Export a session** as a test-fixture folder.
7. **Run and record** the `mp_*` experiment steps. Results and notes go to `manual_test_results.json`.

### F7. Transcription and playback integration

- `Transcription`'s merged-audio entry point becomes the `AudioProcessing` pipeline. The public `TranscriptionEngine.processAudio(micPath:systemPath:customVocabulary:)` contract is unchanged, and so is the XPC request.
- Re-transcribing any existing meeting, including VPIO-era ones, runs the new pipeline. Old recordings have no timeline and usually no detectable echo, so the result is effectively levelled and mixed.
- Meeting playback uses `mic.processed.aac` when it exists next to `mic.aac`, and `mic.aac` otherwise. The system track's playback is unchanged.
- `AudioMerger` and its tests are removed. Its behaviour is covered by the mixer's tests.

## 5. Edge cases

| Case | Expected behaviour |
|---|---|
| Headphones (no acoustic echo) | Alignment finds no echo, so AEC is skipped. Levelling only. |
| AirPlay or another long-latency output (about 2 s) | The aligner searches up to +2.5 s, so echo is found and pre-aligned. Beyond that, AEC is skipped with a recorded reason. |
| Bluetooth HFP mic (AirPods), 16 or 24 kHz, 1 channel | Passthrough: no channel files, normal processing. |
| Built-in mic flips 1↔3 channels mid-recording | New segment, recorded in the timeline. Each segment is combined separately, and gain is allowed to reset at segment boundaries. |
| Multichannel interface with the mic on input 2 and input 1 empty | Input 1 never goes live, so it's deleted at segment end. `mic.aac` = input 2 (the mean of live channels). The channel plan picks input 2. |
| Interface with two people on two mics | Both channels are live and uncorrelated, so both are summed. |
| An unconnected interface input with preamp noise (live but no speech) | Excluded from the plan by its SNR gate. Included in `mic.aac`'s mean, a known fallback cost of about −3 dB plus noise. |
| A device with more than 16 inputs | The first 16 are captured; a warning is logged. |
| System track lost mid-recording | `system.aac` is shorter. Mixing pads it with zeros; AEC runs only where a reference exists. |
| Mic never live (permission, hardware, lid closed) | `micSuspectedSilent` is raised. Processing produces a system-only mix, with a warning in the report. |
| Very short recording (under 5 s) | All stages run. Alignment usually reports no echo. Levelling falls back to whole-file statistics. |
| Double-talk | The engine's double-talk handling applies. Leveller gain is measured on near-end-only frames. |
| Clock drift between devices | The aligner fits per-segment drift, and the engine handles the residual. |
| A gap fill in either track | Segment boundary for alignment: the delay is re-estimated per segment. |
| Re-processing (re-transcribe) | Overwrites `mic.processed.aac` and `processing.report.json` atomically; raw files are untouched. |
| Crash during recording | `mic.aac` and `system.aac` stay readable (ADTS). Channel files are ADTS too, so they're also readable. The timeline can end without a `stop` event, and readers tolerate that. |

## 6. Constraints

- **Platform:** macOS 15+, Apple silicon only, Swift 6 language mode, warnings as errors (repo convention).
- **Licences:** permissive only (BSD, MIT, Apache-2.0). Attribution goes in `THIRD_PARTY_NOTICES.md`.
- **Runtime:** no network access, no model downloads. Any model weights ship in the bundle.
- **Distribution:** the vendored C/C++ must build under hardened runtime and notarisation. No JIT; CPU-only backends.
- **Privacy:** all processing stays on-device. Lab exports go to user-chosen local folders only.
- **The capture layer must stay real-time safe:** no allocation and no locks held across I/O in the tap callback (existing `MicCaptureSession` rules).

## 7. Testing requirements

- **Automated (`make test`):**
  - Generated real-speech scenarios with known ground truth, covering every processing stage and the edge cases above that can be simulated offline.
  - Capture-layer unit tests with fake engines and synthetic multichannel buffers. These include writing real AAC through the real 48 → 24 kHz path, per [the hardware debugging workflow](../../research/audio/hardware_debugging_workflow.md).
  - Timeline round-trip and contract tests.
- **Bake-off:** `audioproc-cli bakeoff` (and `make bakeoff`) produce a committed markdown report.
- **Manual:**
  - The `mic_pipeline` script (`mp_*`) runs in the lab at Checkpoint 1.
  - The existing `ac_*` and `tx_*` scripts are re-run at Checkpoint 2, following the staleness rule.

## 8. Acceptance criteria

1. **No disruption.** On hardware, a Chrome/Meet call, a Slack huddle and a native Teams call on the built-in mic are unaffected by starting and stopping a Biscotti recording:
   - the far end confirms they hear no change;
   - the webcammictest.com before/after recording sounds the same;
   - the output device's sample rate doesn't change;
   - other apps' playback is not ducked.
2. **No lost mic data.** Every channel with signal is recorded. The interface-on-input-2 scenario produces a non-silent mic track.
3. **Levels.** On lab recordings, the user's speech loudness in the transcription mix is within ±3 dB of the remote speech loudness, in both passive modes (1-channel and raw array).
4. **Echo.** On speaker-mode lab recordings, the estimated ERLE with the selected engine is ≥ 10 dB, and the transcript doesn't attribute remote speech to the local mic in far-end-only regions (checked by listening and reading).
5. **Compatibility.** VPIO-era meetings re-transcribe successfully. Playback works for old and new meetings.
6. **Green builds:** `make ci` is green, and the bake-off report is committed.
7. **Manual tests:** `mp_*`, `ac_*` and `tx_*` have been run on hardware and committed.
