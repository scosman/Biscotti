# Open-source macOS meeting recorders and voice apps: how they capture the mic

**Researched:** 2026-10-28, from shallow clones (commit SHAs below) read as data, never built or run. Issue and changelog text was read from GitHub. The VPIO case histories (MacParakeet, Transcripted, OpenOats, Screenpipe, Humla, Vext) are in [vpio-case-studies.md](./vpio-case-studies.md). This file covers every app's capture architecture, including those.

## Notes per app (beyond the matrix)

### anarlog / Hyprnote (the most mature software-AEC design)

The README says: "The team is now building char … The anarlog community application remains open-source, MIT-licensed." The repo moved from `fastrepl/hyprnote` to `fastrepl/char` to `fastrepl/anarlog`.

- **Mic path** (`crates/audio-actual/src/mic.rs`). It opens the selected or default device through cpal's `default_input_config()` and downmixes interleaved frames to mono **by averaging all channels** (`rt_ring.rs:12`, `sum / channels`). No VPIO anywhere. MacParakeet's review independently confirms this: "Current Char/Anarlog source … does not show VPIO, `setVoiceProcessingEnabled`, `VoiceProcessingIO`, `AVAudioEngine`, or `AVAudioInputNode` usage."
- **System path** (`speaker/macos.rs`). `TapDesc::with_mono_global_tap_excluding_processes([])` plus a private aggregate device.
- **AEC** (`crates/aec`, `capture/stream.rs`). A two-stage ONNX model with 512/128 block and shift, LSTM state size 128/256/512, and a "lpb" (loopback) input. These names and shapes match [breizhn/DTLN-aec](https://github.com/breizhn/DTLN-aec) (MIT; `dtln_aec_128/256/512`, `*_lpb.wav`). *That attribution is my inference; the crate does not name its source.* Before the model, `AecReferenceAligner` estimates a stable mic-to-speaker lag (max 600 ms, min 400 ms overlap) and delay-lines the earlier stream. After the model, `cancel_linear_echo` removes residual correlated echo, with a gain clamp (1.25), smoothing, and a double-talk residual ratio. The stage runs only when both mic and speaker are live.
- **When AEC is enabled** (`crates/listener-core/src/actors/source/stream.rs:50-73`): `enable_aec: !no_aec_override && !headphone_output`. Here `headphone_output` means *every output currently playing* is a headphone. "Headphones make AEC pure cost: it burns CPU and can degrade near-end speech. The check covers every output that is playing, not just the default, because meeting apps pick their own speaker." A routing watcher re-evaluates the decision live.
- **What is recorded and transcribed.** `CaptureFrame.preferred_mic()` returns the AEC output when present, else raw (`crates/audio/src/lib.rs:47`). The pipeline then VAD-masks the mic, zeroing non-speech frames (`pipeline.rs:148`). Both the recorder and STT get this processed mic.
- **History** (repo changelog): 1.0.2 (2026-01-30), "Acoustic Echo Cancellation (AEC) eliminates the need for heuristics-based micOnly mode" and "Record microphone and speaker as separate stereo channels". 1.0.27, "Echo cancellation now better aligns speaker audio with microphone input". 1.3.10, "Improve echo cancellation for larger speaker and microphone timing differences". 1.4.18 (2026-09-04), "Skip echo cancellation when your default output is a headphone" and "Record from a wired or built-in microphone when the default input is a Bluetooth headset, avoiding the muffled, gated call-mode mic".
- **Known problem.** [#4560](https://github.com/fastrepl/anarlog/issues/4560) (2026-03-13, open): with a Logitech Brio webcam mic and MacBook speakers, "AEC causes the transcript to fragment into single words alternating between speakers." It lists earlier AEC issues #4314, #3096 and #1428, which I could not open (404).

### Meetily (a mixed track with a fixed-gain normalizer)

- `audio_to_mono` (`frontend/src-tauri/src/audio/audio_processing.rs:478-500`): "For microphone arrays (> 2 channels), only use first 2 channels. Many microphone arrays have auxiliary channels for beam-forming/noise cancellation that can contain anti-phase signals. Averaging all channels can cause destructive interference resulting in near-zero output."
- The mic chain is high-pass (80 Hz) → RNNoise (off: "Whisper handles noise well internally - RNNoise is optional", `ffmpeg_mixer.rs:20`) → stateful EBU R128 normalizer to −23 LUFS with a true-peak limiter (`pipeline.rs:525-585`).
- Mic and system are summed into **one** recording ("Raw audio is NOT sent to recording saver to prevent echo"). Feature request [#241](https://github.com/Zackriya-Solutions/meeting-minutes/issues/241) asks for separate tracks.
- Issue [#220](https://github.com/Zackriya-Solutions/meetily/issues/220) (2025-10-25, Windows, Teams): "the echo was coming from the laptop microphone picking up the speakers output … when I used a headset … the issue went away." The maintainers replied that processing must stay local and open-source. It is still open.

### Muesli, Meeting Transcriber, Prismical, Corti (software AEC on a raw mic)

- **Muesli** (`MeetingNeuralAec.swift`): "Mic and CoreAudio tap callbacks are delivered on independent queues. Keep mic frames pending and system audio in a history buffer so the AEC model can receive the far-end frame that matches the mic frame's sample position." LocalVQE comes first (`localvqe-v1.2-1.3M-f32.gguf`, bundled; `LocalVQEProcessor.swift:29`), with DTLN-aec (CoreML, `DTLNAecCoreML_DTLNAec512.bundle`) as fallback, and up to 48,000 samples of reference wait. *Note the conflict:* MacParakeet's synthetic harness found this same joint v1.2 model "zeroes the near-end voice" and picked the echo-only v1.4-aec model instead. Model choice is a near-end-retention risk, which the post-processing subtopic should check.
- **Meeting Transcriber** treats echo as something to *detect and report*. `EchoBleedDetector.swift` explains why a whole-file correlation fails: "a reproduced echo recording measured 0.92 inside its echo phases and 0.657 across the file". Clean recordings reach window maxima of 0.3 to 0.55; affected meetings had 34%, 60% and 77% of windows above 0.7. Both remedies (LocalVQE cancel and transcript dedup) are off by default. The dedup is off "because it can mistake a quiet remark made over the far end for echo".
- **Prismical** (`LiveAecSession.swift`) uses AEC3 at 48 kHz with 10 ms frames, ingests render (system) before capture (mic), and holds the mic back by 300 ms with a render-wait timeout.
- **Corti** sidesteps alignment entirely. It builds one aggregate device whose clock master is the default mic and whose tap list holds the process tap, so "mic + far-end audio on one shared clock — no … two-stream alignment" ([`design/LESSONS.md`](https://github.com/vasovagal/corti/blob/main/design/LESSONS.md)). *For Biscotti, this matters for any post-processing AEC: our two tracks are on separate clocks.*

### OBS Studio (pro-audio handling of multichannel inputs)

`plugins/mac-capture/mac-audio.c` opens an **AUHAL** (`kAudioUnitSubType_HALOutput`, line 628) and either downmixes all device channels (default `enable_downmix = true`) or applies a user-chosen per-output-channel map via `kAudioOutputUnitProperty_ChannelMap`, read from settings `output-<device>-<n>` (lines 289-325, 795-838). Before the channel map was added, users with 12-input mixers had to route through Loopback or Audio Hijack ([issue #2556](https://github.com/obsproject/obs-studio/issues/2556), 2020). Noise suppression is Speex or RNNoise (`plugins/obs-filters/noise-suppress-filter.c`). There is no AEC filter, and users route through Audio Hijack for Apple's `AUSoundIsolation` ([forum](https://obsproject.com/forum/threads/apple-audio-units.168775/)). Open [PR #11933](https://github.com/obsproject/obs-studio/pull/11933) reads `AVCaptureDevice.activeMicrophoneMode` to warn users, because "macOS system effects operate on a 'per-application' basis rather than 'per-device'". The author also reports Wide Spectrum "seems unavailable in OBS for any audio devices in my testing, even those that constitute multi-mic arrays on recent Apple Silicon devices."

### Reference implementations

- **AECAudioStream** ([kasimok/AECAudioStream](https://github.com/kasimok/AECAudioStream), last commit 2023-06-16): a Swift wrapper over `kAudioUnitSubType_VoiceProcessingIO`. MacParakeet flags it as "this will hit the exact same conflict because it wraps the same underlying AU."
- **AudioCap** ([insidegui/AudioCap](https://github.com/insidegui/AudioCap)): tap-only sample with no mic. The pin-main-subdevice-by-UID pattern comes from here.

## What the OSS field converged on (inference from the matrix)

1. **A plain, non-VP mic plus a separate system track** is the norm. Of the ~19 apps above, only TypeWhisper enables VPIO by default today, and only when the built-in mic is in its 3-channel call layout. Three meeting recorders shipped it unconditionally and reverted (MacParakeet, Transcripted, OpenOats; see the case studies). Screenpipe and MacParakeet keep it as an opt-in, and Transcripted keeps it behind consent.
2. **Echo is handled in software against the system track**, at one of three layers:
   - live neural or classical AEC: anarlog (DTLN-style), Muesli (LocalVQE/DTLN), Prismical (AEC3), Corti (FDAF), Screenpipe and OpenWhispr (AEC3, opt-in)
   - offline AEC after stop: MacParakeet (LocalVQE), Humla (MDF), Meeting Transcriber (LocalVQE, opt-in)
   - transcript-level dedup only: OpenOats, Vexa, Screenpipe (display layer)

   Several stack two layers.
3. **Turn AEC off when on headphones.** anarlog does this automatically. Granola's dormant native addon has a `disable_echo_cancellation_on_headphones` flag (see [commercial-apps.md](./commercial-apps.md)). Recall.ai advises it.
4. **Levelling is done in software**: Transcripted's real-time AGC, Meetily's EBU R128, Granola's dormant `automatic_gain_compensation`. None of these recovers speech that another app's voice processing has already gated; Transcripted states this explicitly.
5. **Averaging a multichannel built-in array is widely treated as a bug.** Fixes chose channel 0 (OpenOats), the strongest channel (Transcripted, TypeWhisper), or the first two channels (Meetily). anarlog and Corti still average. See [multichannel-and-levelling.md](./multichannel-and-levelling.md).
